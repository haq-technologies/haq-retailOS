# Decision log

Every product and build decision taken since spec v1.4, and where it came from. Spec v1.5 applies all of them; its tags ([S4], [R3], [D2], [Q5], [FU6]) point here.

Sources:
- **Register:** the decision register in the review doc "HAQ Retail OS: Spec v1.4 Review and Build Plan" (https://claude.ai/artifact/DW5VWtw3J6xgMg6xMSgKSY).
- **Q1 to Q24 and FU1 to FU10:** that doc's questions and follow-up questions. The doc labels the follow-ups F1 to F10; here they are FU1 to FU10, so they never clash with the teardown findings F1 to F25 in the spec.
- **Correction:** a fix with no real alternative, listed in the review and adopted because nobody objected.
- **Chat:** decided in conversation with Claude.

To add a decision, give it the next ID in its series, the date and the source, then update the spec (with the tag) and PLAN.md if the schedule changes. Never rewrite an old row: mark it superseded and add a new one.

| D44 | Restore recovery end to end (spec sections 4 and 9; check B9) [F1, S14]. Each restore is recorded, and each counter reports its journal at start, on reconnecting, and when Finish answers that the server was restored: first the highest receipt number it holds in each epoch, then the sales the server lacks. Receipt numbers are per counter, so the wait is per counter: a counter whose epoch began with a restore sells again once it has reported, and a broken counter never stops the others; this is how the spec's "trading resumes only when each enrolled counter has reported" is met. The report raises the counter's epoch past anything its journal shows, numbering from 1,001, also when nobody recorded a restore (a copy put back by hand) and on a reinstalled server with no epochs. A manager or the owner re-enters each lost sale on the lost-window screen (Lost sales, shown after a restore and while a sale waits) as a back entry under the receipt number the customer holds, with its original time, cashier, lines and payments; it prints nothing, counts in every report like any sale, is flagged as re-entered and is audited. A line whose item the restored data lacks is recorded under an item the manager chooses and keeps its printed name. The journal keeps the item, cashier, business day, colour, cash given and transfer reference, never cost. A restore gives the catalogue feed a new generation, so every counter takes a fresh copy.
